# 缓存与成本分析（2026-11-15）

M3 第 4 步。分析对象是[A/B 报告](./2026-11-15-ab.md)里采用的配置的那次全量运行：51 个用例，`claude-opus-5-5` / `high`，`method-latency@2`，补录后的快照。数据来自这次运行在 Tempo 里的 trace 和 Prometheus 的 `incident_llm_*` 指标，两个来源的总数一致。没有为这份分析额外调用 Claude API。

## 结论

**不建议改动。** 缓存已经按设计工作，剩下的免费手段收益都很小，能明显降低成本的手段（降 effort、换模型）在 A/B 里量过，都要付出准确率。

- 每次调查平均 0.18 美元，最高 0.39 美元，低于 `AGENT_MAX_COST_USD` 的 0.6 美元上限，没有调查触顶。
- 缓存命中率 82.5%，未缓存的输入每次调查只有 14 个 token。

## 费用构成

调查步骤，51 次调查共 308 次模型请求：

| 类别               | tokens 合计 | 每次调查 | 费用      | 占比  |
| ------------------ | ----------- | -------- | --------- | ----- |
| 未缓存输入         | 718         | 14       | 0.00 美元 | 0.0%  |
| 缓存读取           | 3,738,590   | 73,306   | 0.75 美元 | 8.3%  |
| 缓存写入（5 分钟） | 790,154     | 15,493   | 3.95 美元 | 43.8% |
| 输出               | 215,665     | 4,229    | 4.31 美元 | 47.9% |
| 合计               |             |          | 9.01 美元 |       |

- 输出里有 35,100 个 reasoning token，占输出的 16%。
- 分诊（`claude-haiku-5-5`，51 次请求）合计 0.02 美元，可以忽略。
- 每次调查的费用分布：3 个不超过 0.10 美元，35 个在 0.10 到 0.20 之间，9 个在 0.20 到 0.30 之间，4 个在 0.30 到 0.50 之间。

## 轮数、工具调用与时延

- 每次调查的模型请求数：最小 4，中位 6，p95 9，最大 11。没有调查达到 `AGENT_MAX_TURNS`（12）。
- 每次调查的工具调用数：中位 13，p95 21，最大 27，平均每次模型请求并行约 2.7 个。`query_metrics` 317 次，`query_logs` 216 次，`get_service_status` 69 次，`propose_action` 45 次，`search_knowledge` 44 次。
- 停止原因：257 次 `tool_use`，51 次 `end_turn`，没有 `max_tokens`、`refusal` 和 fallback。308 次请求的 effort 都是 `high`。
- api 内部的调查耗时平均 46.7 秒：模型请求占 86%，分诊 6%，检索 2%，工具调用 1%（回放模式，真实后端会更慢）。评估报告里的 88.6 秒是 promptfoo 端量的，包含并发 4 下的排队和轮询。

## 逐项判断

| 手段                     | 判断           | 理由                                                                                                                                                                          |
| ------------------------ | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 提示缓存                 | 已到位，不动   | 命中率 82.5%。每轮的写入量约等于那一轮新增的工具结果，没有发现让缓存失效的内容。                                                                                              |
| 1 小时缓存               | 不用           | 一次调查只持续 30 到 60 秒，5 分钟足够。1 小时写入更贵，只有告警密集到能跨调查复用前缀时才划算，评估数据说明不了线上的告警间隔。                                              |
| 压缩工具结果             | 收益小，暂不做 | 工具结果本来就是摘要：多数 0.4 到 3 KB，按操作拆分的 p95 最大约 11 KB。把多条序列的时间戳合并成一份估计能省下总费用的百分之几，但要改 contracts、重新补录全部快照并重跑评估。 |
| 减少输出                 | 没有明显空间   | 每次请求约 700 个输出 token，主要是工具调用参数和最终报告。                                                                                                                   |
| 降低轮数上限             | 无效           | 没有调查触顶。                                                                                                                                                                |
| Batch                    | 不适用         | 调查是带工具的多轮循环，且对时延敏感。                                                                                                                                        |
| effort 降到 `medium`     | 不采用         | A/B 里费用少约 12%，top-3 从 47/51 到 44/51，没有显示出优势。                                                                                                                 |
| 换成 `claude-sonnet-5-5` | 不采用         | A/B 里费用约为 40%，top-3 为 36/51，低于 SLO。                                                                                                                                |

最贵的 5 次调查里有 3 次是 imageSlowLoad 场景：frontend-proxy 的日志和按操作拆分的结果都大，缓存写入是平均值的 2 到 3 倍。如果以后要压缩工具结果，从这里入手。

## 局限

- 评估以并发 4 连续运行，稳定前缀（工具、系统提示、拓扑）在调查之间也能命中缓存。线上告警稀疏时，每次调查的第一个请求要重新写入前缀，单次成本会略高于这里的数字。
- 评估结果文件里的 `usage` 只有总输入、总输出和费用，分不出缓存读写；本报告的拆分来自 trace 和指标。
- 只分析了一次运行。
