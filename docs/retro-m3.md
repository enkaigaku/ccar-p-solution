# M3 阶段复盘：评估驱动优化

M3 的目标是用评估把 M2 集成出来的调查流程调到 SLO 达标（门禁 G3）。本文记录做了什么、结果如何、哪些判断是对的、哪些地方走了弯路，供下一阶段参考。数字都来自 `packages/evals/reports/` 下的 5 份报告，这里只做汇总，细节和局限以报告为准。

时间上 M3 集中在 2026-11-14 到 11-15，对应 PR #18 到 #27。

## 结论

**G3 通过。** 同一配置跑了两次全量（各 51 个真实故障用例），准确率、引用、安全、调查时延和缓存命中率都达标，两次结果一致。单次调查成本按平均值达标，但每次运行有 3 到 4 条超过 0.30 美元；分诊延迟 p95 在阈值边缘。

| 指标              | 目标        | M2 结束时的基线 | M3 结束时（两次）               |
| ----------------- | ----------- | --------------- | ------------------------------- |
| 根因 top-1        | ≥ 70%       | 90.2%           | 94.1%、94.1%                    |
| 根因 top-3        | ≥ 85%       | 92.2%           | 96.1%、94.1%                    |
| 引用有效性        | 100%        | 51/51           | 51/51                           |
| 未审批写操作      | 0           | 0               | 0                               |
| 调查时延 p95      | ≤ 90 s      | 118.4 s         | 65.8 s、75.9 s                  |
| prompt 缓存命中率 | ≥ 70%       | 没有量          | 82.5%、83.0%                    |
| 单次调查成本      | ≤ 0.30 美元 | 平均 0.17       | 平均 0.18，每次有 3 到 4 条超出 |

基线的时延是 promptfoo 端量的，包含排队和轮询；M3 结束时取的是 api 内部 span 的耗时。两者口径不同，时延这一行不能直接相减。

这些结果只对这套用例成立。模型认识 OpenTelemetry Demo，runbook 语料里也写着 flag 名与症状的对应关系，不能外推到陌生系统。

整个阶段的 API 花费约 71 美元（月度上限 500 美元），用了 7 次全量评估和 17 次冒烟评估的额度。

## 关键决策

1. **调查保持 `claude-opus-5-5` / `high`。** `medium` 的时延少约 15%、费用少约 12%，但 top-3 从 47/51 降到 44/51，没有显示出优势。Sonnet 的费用约为 40%，top-3 只有 36/51，低于 SLO，而且风格明显更保守（19 条提出处置建议，Opus 是 43 条）。
2. **延迟调查先按操作拆分，再按被调用方拆分。** 基线暴露出服务级 p95 既会被占比小的慢请求稀释，又会被长连接 span 污染。改工具说明和方法提示后 top-3 从 47/51 到 49/51，没有用例由命中变未命中。
3. **缓存不动。** 命中率 82.5%，未缓存的输入每次调查只有 14 个 token，没有可压的空间。
4. **缩短日志样本不采用。** 平均只省 3% 到 4%，没有把超标的调查压到 0.30 美元以下，准确率上还有一条排除不掉的疑点。代码没有合入。
5. **检索保留。** 有检索和无检索的准确率只差 2 条，在单次运行的波动之内；稳定的差别是有检索时 43 条提出了处置建议，无检索时 29 条。检索的价值主要在「敢不敢给出处置」上。

## 做对了什么

- **先校准 judge，再相信分数。** rubric@1 和人工打分的一致率只有 86.7%，不到 90% 的门槛。如果直接用它，基线会少算命中，后面每个对比都建立在不可信的尺子上。
- **`rejudge` 把「改尺子」和「重跑 agent」拆开。** 评分说明改动后，两份基线用 0.61 美元重新打分，而不是再花 18 美元重跑。
- **带干扰故障的用例分开统计。** 26 条带干扰的用例让「agent 把无关故障当根因」变得可以量，也让 Sonnet 的弱点（23/26 降到 17/26）显现出来。
- **读审计日志找失败原因，而不是猜。** 两条稳定失败的用例，是从 api 审计里逐条看工具调用才发现 agent「没有一次查过 shipping」，问题不在推理而在它没有理由去查。对症的改动因此是给它一个能区分下游的查询。
- **同一配置跑两次。** 第二次运行确认了 top-3 的波动约 1 条，也把「稳定失败」和「时过时不过」的用例区分开。没有这一步，前面 2 到 3 条的差距都可能被当成结论。
- **不采用的做法也写进报告。** 缩短日志样本的验证过程和放弃的理由都留着，下一个想到这个主意的人不用再花钱试一次。
- **回放让优化便宜且可重复。** 所有对比都在同一批录制快照上做，差异只来自 agent 的配置。

## 没做好的地方

- **多数对比只跑了一次。** A/B 的三种配置各一次，`medium` 比基线少的 3 条恰好都是不稳定的用例，严格说不足以证明它更差。两次运行的做法应该从基线就开始，而不是到 SLO 验证才补上。
- **judge 的校准不独立。** rubric@2 是参照同一批 30 条样本里的不一致改出来的，96.7% 的一致率偏乐观。`cartFailure` 的样本偏少，Sonnet 那 6 条 partial 也说明 judge 的口径不完全一致。
- **工具说明改了之后要补录快照，事先没有预料到。** 回放按 PromQL 逐字匹配，新增一种查询写法就要给 51 个快照补录，为此临时写了 `evals backfill`。它依赖 Prometheus 还留着当时的数据（本地 15 天），这个窗口过了就只能重新录制。
- **成本目标的口径一开始没有定。** 设计文档没写 0.30 美元是按平均值还是按每一次调查，到 SLO 验证时才发现两种读法结论不同。现在的状态是「平均达标，个别超出」，没有收口。
- **追加的修复没有跑全量。** `method-latency@3` 改了对所有用例都生效的工具说明，却只在 19 条上验证。当时全量额度只剩 1 次；这是一个预算换来的缺口，不是验证充分。
- **修一个线索，伤了另一个。** 把容器重启次数标明为累计值，修掉了国际运费慢被归因到 email 的问题，也让 emailMemoryLeak 的置信度下降，其中 1 条不再提出处置建议。
- **trace 里不记工具调用的入参和结果大小。** 分析成本时不知道 agent 自己带 `limit` 的调用有多少，缩短日志样本的验证因此量不清楚实际生效了多少次。
- **未命中用例没有保存 judge 的理由。** 回头分析 Sonnet 的 partial 时只能重新推断。

## 教训

1. **评估的结论要带着它的方差一起报告。** 51 个样本下 1 条就是 2 个百分点。没有重复运行，就不要下「A 比 B 好」的结论，只能说「没有显示出差别」。
2. **稳定的失败比平均分更有信息量。** 两次都错在同一个地方的用例指向一个具体的缺陷；时过时不过的用例多半是数据本身信号太弱（低比例的 cart 故障在窗口内只有 1 次错误）。
3. **agent 的错常常是「没有可用的查询」，不是「不会推理」。** M3 里两次有效的改进都是给工具说明加一种查询写法，方法提示只是告诉它什么时候用。
4. **回放的保真度决定了能优化什么。** agent 自己发明的查询在回放里得不到数据，日志回放也不随时间窗口变化，所以「故障前后对比」这类能力在这套评估里量不出来。
5. **预算是设计约束，不是事后统计。** 每月 8 次全量的额度逼着把每次运行要回答的问题想清楚，也直接决定了哪些验证做不了。
6. **目标要写明口径。** 「单次成本 ≤ 0.30 美元」这样的 SLO，平均值、p95 还是每一次，要在定目标的时候写下来。

## 遗留事项

按价值排序，前两项针对的是已知的稳定缺陷。

1. 用 `method-latency@3` 跑一次全量，确认 19 条之外没有回退。
2. 容器重启改为带时间的信息（窗口内的增量或最近一次启动时间）。要改 contracts，历史快照补录不了，需要重新录制。
3. shipping 的 runbook 写的是 `intlShippingSlowdown` 拖慢 GetQuote，与实际不符，导致 agent 不敢提议关闭这个 flag。
4. 在工具调用的 span 上记录结果大小和 `limit`，再决定怎么处理 imageSlowLoad 的成本。
5. 增加「处置建议所针对的组件是否为标准根因」的指标。`fc-bcd25bc1` 曾两次对错误的根因提出处置建议。
6. 补充独立的 judge 校准样本，并保存未命中用例的 judge 理由。
7. 用模型不认识的系统或改名后的服务做一组用例，检验结论能否外推。
8. 定下成本目标的口径。
