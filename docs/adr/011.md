# ADR 011：反馈闭环：复盘草稿经审核回写知识库，线上反馈整理成评估用例

- 状态：已接受
- 日期：2026-11-15

## 背景

设计文档要求两条回流：事件结束后生成复盘草稿，审核后回写知识库；控制台的赞 / 踩和「实际根因」落库，并定期挑进评估集。合入本 ADR 之前两条都没有做，反馈只存在 api 进程内存里。

两条回流都把线上内容送回系统自己会读的地方：复盘进入 agent 检索的知识库，反馈进入衡量 agent 的评估集。所以要回答的不只是怎么存，还有谁有权让内容进去。

## 决定

**反馈落库，自带报告快照**

- 反馈写入 Postgres 表 `api_feedback`（没有 `DATABASE_URL` 时退回内存）。每条记录带提交人和提交时的报告快照（告警、假设、prompt / index / 模型版本、trace id）。调查本身仍在内存里，快照让反馈在 api 重启后依然完整，也不会被同一告警的后续调查改写。
- 记录以契约 Schema 的 JSON 编码存在一个 `jsonb` 列里，旁边只放查询要用的列。Schema 是唯一的结构定义，不再维护一套逐列映射。
- 自由文本（实际根因、评论）不进 span 和日志。span 上只有反馈 id、评分、是否带根因，以及原调查的 trace id。原 trace 已经结束，无法再追加 event，所以用属性关联，而不是设计文档里写的 span event。

**复盘草稿：模型起草，人审核，审核通过才入库**

- 起草是一次 Sonnet 5.5 调用（effort `medium`，structured output，开启服务端 fallbacks），输入是告警、假设及其证据、提议及结果、响应者反馈，全部包在 `<untrusted-data>` 里。响应者写了实际根因时以它为准，并写明调查当时的结论。
- 草稿正文是五个固定字段，由 api 渲染成 Markdown。四个 H2 小节正是知识库对复盘切块的边界，模型不能决定文档结构。
- 状态只有 `draft` → `published` 或 `rejected`。responder 可以生成和修改草稿；**发布需要 approver**，因为发布决定了 agent 之后会把什么当作参考资料，和批准写操作是同一级别的决定。发布写审计（谁、哪个文档、哪个 index 版本、全文）。
- 草稿的 id 标识正文的一个版本：每次修改（和重新生成一样）都换一个新 id。审核请求带的是审核者页面上那一版的 id，正文在他阅读期间被别人改过时，旧 id 已不存在，请求得到 404，需要刷新后重新审核。这样审批绑定在审核者实际看到的正文上，不需要在审核请求里另带版本号。
- 发布时先把 Markdown 写到 `POSTMORTEM_CORPUS_DIR`（默认 `infra/.api-state/corpus/postmortems/generated/`），再通过 `Ingestor` 增量写入并激活。ingest 失败时删掉刚写的文件，草稿保持 `draft`，可以重试。目录里因此只有已发布的复盘，带 `--also` 的全量重建不会读到被拒绝或被替换的草稿。

**生成的复盘不进仓库里的语料目录**

- `rag ingest` 的全量重建默认只读 `packages/rag/corpus/`，重建后的索引不含生成的复盘。要带上它们，加 `--also infra/.api-state/corpus`。
- 理由：评估的基线是「仓库里的语料」这个确定的状态。生成的复盘来自线上事故，其中一些就是评估集里故障的答案；默认带上它们，评估分数会随着线上发生过什么而漂移。

**反馈整理成评估用例：候选 → 人工复核 → 提升**

- api 给每次观测工具调用多写一条 `tool_call` 审计记录，内容是契约里的 `RecordedToolCall`（输入加结构化输出，已在 mcp-observability 里脱敏）。
- `evals curate` 读取带实际根因的反馈和审计日志，为每个调查生成一个候选：回放快照来自审计里的工具调用，标准答案来自响应者写的根因。候选写在 `packages/evals/candidates/`（不进 git）。
- `evals promote <id>` 在人工复核后把候选移入 `datasets/feedback/` 和 `fixtures/replay/`。用例是新的一类 `feedback`，id 不透明（`fb-xxxxxxxx`，由调查 id 的哈希得到）。

## 备选方案

- 草稿生成后直接入库，事后再删：最省事，但 agent 会把另一个模型未经确认的结论当参考资料读回去，错误会自我强化。
- 让模型直接输出 Markdown：少一层渲染，但文档结构、front matter 和标题都变成模型可控（也就是告警文本可间接影响）的内容。
- 生成的复盘写进 `packages/rag/corpus/` 并提交：复盘可以走 PR review，但 api 需要对仓库的写权限，而且评估基线会被线上数据污染。
- 反馈直接变成评估用例，不经人工：响应者写的「实际根因」是随手写的一句话，服务归属是猜的，还可能带不该进仓库的内容。
- 把业务状态（告警、调查、提议）一起迁到 Postgres：值得做（交接文档第 1 项），但和反馈闭环是两件事，本次不做。

## 后果

- 反馈用例的快照只包含 agent 当时问过的查询，不像录制器那样把一组查询全扫一遍。prompt 改了以后 agent 换一种问法就会拿到空结果。这类用例上的回退是「值得看一眼」的线索，分数不能和故障集混在一起比较。所以 `smoke` / `full` 不选反馈用例，它们用 `eval:feedback` 单独跑；`rejudge` 汇总和 `gate` 把它们单列，不进故障集的准确率分母，也不设准确率门禁。
- 候选能否生成取决于审计日志：调查发生在本改动之前，或者审计文件不是那台机器上的，就没有 `tool_call` 记录，`curate` 会说明跳过的原因。
- 每周的整理仍然是人工触发的命令，没有定时任务。
- 调查仍在内存里：api 重启后，旧调查的复盘端点返回 404，但已发布的复盘在知识库里，已落库的反馈和草稿在表里。
- 发布后的复盘不能修改或撤回。要撤回，用空 Markdown 对同一个 `sourceId` 再 ingest 一次（`Ingestor` 的删除语义），并删掉对应文件。
