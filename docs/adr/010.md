# ADR 010：控制台用 OIDC 登录，api 作为资源服务器校验访问令牌

- 状态：已接受
- 日期：2026-11-15

## 背景

「任何写操作必须经人工审批」是硬约束，但合入本 ADR 之前 api 没有认证，审批人是环境变量里的固定值，无法证明是谁批准的。设计文档要求控制台用 OIDC 登录（本地用 Keycloak），角色分 viewer / responder / approver。

## 决定

- **web 是 OIDC 客户端（BFF）**：授权码流程 + PKCE，用 `openid-client`。令牌只保存在 web 服务端的内存会话里，浏览器只有一个不透明的 `HttpOnly`、`SameSite=Lax` 会话 cookie。`/api` 代理把 cookie 换成该用户的访问令牌，丢弃浏览器自带的 `Authorization`，并拒绝跨站的写请求。
- **api 是资源服务器**：用 `jose` 校验访问令牌的签名（JWKS）、算法（只接受 RS256 / PS256 / ES256）、`iss`、`aud`（`incident-api`）和有效期，把 `sub` 与角色映射成契约里的 `Principal`。角色在 handler 里用 `requireRole` 校验：读取为 viewer，发起调查和反馈为 responder，审批为 approver。SSE 路由不在 HttpApi 里，用同一个校验器自行检查。
- **审批人来自令牌**：`ApprovalToken.approver` 和审计记录用 `sub`，`ActionProposal.decidedBy` 用显示名。批准和拒绝都写审计。
- **没有静默降级**：没有 `OIDC_ISSUER` 时 api 拒绝启动，除非显式设置 `AUTH_MODE=dev`（所有请求视为拥有全部角色的固定操作员，启动时告警）；两者同时设置也拒绝启动。评估和本地控制台开发用 `AUTH_MODE=dev`。
- **角色的层级放在身份提供方**：Keycloak 里 approver 是包含 responder 和 viewer 的复合角色，api 的每个端点只检查一个角色。

## 备选方案

- 浏览器直接持有令牌（SPA + PKCE）：令牌暴露给页面脚本，XSS 的后果更大；现有的同源 `/api` 代理正好可以承担 BFF。
- 会话放在加密 cookie 里：不需要服务端状态，但令牌仍然到达浏览器，且 Keycloak 的令牌容易超过 cookie 大小限制。
- api 调 Keycloak 的 introspection 端点：能立刻感知吊销，但每个请求多一次网络调用。访问令牌有效期 5 分钟，可以接受。
- 在 api 里自己实现 JWT 校验或 OAuth 流程：不做，协议细节交给 `jose` 和 `openid-client`。

## 后果

- 会话在内存里，web 重启后需要重新登录；多实例部署需要换成共享存储。
- 吊销最长延迟一个访问令牌有效期（5 分钟）；会话最长 8 小时。
- `POST /alerts/webhook` 仍然没有认证，调用方是 Alertmanager / Grafana。它只能新增告警，不能发起调查或审批；需要时再加共享密钥。
- `mcp-ops` 的令牌校验不变：它仍然只信任带有效 `ApprovalToken` 的调用，登录只决定谁能让 api 签发这个令牌。
